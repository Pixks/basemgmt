# Panel użytkownika — pełna dokumentacja funkcjonalna

> **Dokument wygenerowany na podstawie analizy kodu całej wtyczki CampLink v2.0.0-alpha.7.**  
> Nie opiera się wyłącznie na wcześniej pokazanych ekranach — obejmuje wszystkie funkcje wykryte
> w kodzie PHP, JS, szablonach, hookach, endpointach REST, AJAX, cron, bazie danych i konfiguracji.

---

## 1. Zakres systemu

**CampLink** to modularny system zarządzania obozami dla WordPress (PHP ≥ 8.1, WP ≥ 6.0, przestrzeń nazw `BaseMgmt\`).

System obsługuje **dwa konteksty**:

| Kontekst | Dostęp | Interfejs |
|---|---|---|
| **Panel administratora** | Zalogowani użytkownicy WP z capability `manage_basemgmt` lub węższymi | Klasyczny admin WP (`/wp-admin/`) |
| **Panel frontendowy (kadra)** | Kadra obozu uwierzytelniająca się kodem dostępu (bez konta WP) | Single-page application Alpine.js osadzana w Breakdance |

System **nie używa** custom post types, custom taxonomies ani meta boxów — cała logika domenowa opiera się na własnych tabelach SQL (`dbDelta`).

## 2. Architektura funkcjonalna

### 2.1 Warstwa bootstrapu

```
basemgmt.php
  └─ spl_autoload_register (PSR-4: BaseMgmt\ → src/)
  └─ register_activation_hook  → Activator::activate()
  └─ register_deactivation_hook → Deactivator::deactivate()
  └─ plugins_loaded (priority 0) → Bootstrap::instance()->init()

Bootstrap::init()
  ├─ load_textdomain()
  ├─ register_capabilities()    → init: Capabilities::register()
  ├─ register_license()         → LicenseManager::instance()->init()
  ├─ register_admin()           → admin_menu, admin_init, admin_enqueue_scripts, admin_notices
  │                               + 100+ admin_post_{action} handlers
  ├─ register_rest()            → rest_api_init: 12 REST controllers
  ├─ register_frontend()        → init + wp_enqueue_scripts: ShortcodeHandler
  ├─ register_cron()            → init + 10 cron hooks: Scheduler
  ├─ register_notifications()   → ReservationNotifier::register()
  ├─ register_ajax()            → wp_ajax_bm_reorder_plan_items
  │                               wp_ajax_bm_calendar_events
  └─ register_breakdance()      → breakdance_loaded: BreakdanceIntegration
```

### 2.2 Wzorzec Loader

Klasa `BaseMgmt\Core\Loader` zbiera wywołania `add_action`/`add_filter`, a `run()` rejestruje je zbiorczo. Gwarantuje to porządek rejestracji i możliwość testowania.

### 2.3 Wzorzec Repository

Każdy moduł domenowy posiada dedykowaną klasę Repository (izolacja dostępu do DB):

```
Modules/
  Announcements/  AnnouncementRepository
  Camps/          CampRepository, CampCaseRepository, CampSettlementRepository,
                  CampWorkflowAutomationRepository, DailyCountRepository, StaffRepository
  Communication/  ConversationRepository
  Forms/          FormRepository, SubmissionRepository
  Help/           HelpRepository
  Menu/           MealOptionRepository, MealRepository, MealTemplateRepository
  Reservations/   ReservationRepository, ResourceRepository
  Schedule/       PlanTemplateRepository, ScheduleRepository
  Weather/        WeatherAlertRepository
```

### 2.4 Przepływ autentykacji kadry

```
Frontend (przeglądarka)
  → POST /bm/v1/auth/login (loginNonce + camp_id + staff_id + code)
  → AuthController::login()
  → FrontendAuth::attempt()  (wp_check_password na kodzie dostępu)
  → SessionManager::create() (token SHA-256 w DB, hash w ciastku HttpOnly)
  → bm_session cookie (SameSite=Strict, Secure jeśli HTTPS)

Kolejne żądania REST
  → SessionManager::current() odczytuje token z ciastka, weryfikuje hash w DB
  → Wszystkie /panel/* wymagają ważnej sesji
```

### 2.5 Przepływ panelu admina

```
Admin WP
  → check_admin_referer()  (nonce per formularz)
  → current_user_can(capability)
  → admin_post_{action}  → Page::handle_*()  → Repository::*()
```

## 5. Procesy użytkownika

### 5.1 Logowanie kadry (frontend)

```
1. Kadra otwiera stronę Breakdance z panelem
2. Alpine.js komponent bmLogin ładuje listę aktywnych obozów z bmConfig.activeCamps
3. Użytkownik wybiera obóz → AJAX GET /public/camps/{id}/staff
4. Użytkownik wybiera siebie + wpisuje kod dostępu
5. POST /auth/login z loginNonce
6. AuthController: weryfikacja nonce → FrontendAuth::attempt()
7. RateLimiter: sprawdzenie blokady (3 próby → 15 min)
8. wp_check_password() na zahaszowanym kodzie
9. SessionManager::create() → ciastko bm_session (8h)
10. Frontend przechodzi do panelu obozu
```

### 5.2 Meldunek dzienny

```
1. Kadra otwiera zakładkę "Liczebność" lub "Meldunek"
2. Prefill z ostatniego meldunku: GET /panel/daily-count/last
3. Dziś: GET /panel/reports/today (sprawdza czy już wysłano)
4. Tryb roboczy: POST /panel/reports/save (status: draft)
5. Zatwierdzenie: POST /panel/reports/submit (status: submitted)
6. Cron bm_daily_reminders (08:00): email do admina o brakujących meldunkach
```

### 5.3 Rezerwacja zasobu (frontend)

```
1. Kadra otwiera zakładkę "Rezerwacje"
2. GET /panel/reservations/resources (lista zasobów)
3. Wybór zasobu → GET /panel/reservations/slots?resource_id=X&date=Y
4. Formularz rezerwacji z blokadami technicznymi
5. POST /panel/reservations (panelNonce)
6. do_action('bm_reservation_created') → ReservationNotifier
7. Email do admina i kadry (reservation_created)
8. Admin: zatwierdza/odrzuca w wp-admin
9. Email do kadry (reservation_approved/rejected)
10. Cron bm_expire_reservations: wygasanie nieakceptowanych rezerwacji
```

### 5.4 Workflow obozu (automatyzacja)

```
CampWorkflowAutomationRepository::evaluate_all_active_camps()
  wywoływane przez cron bm_camp_workflow_check (07:30 UTC daily)
  → sprawdza etap procesu (process_stage) dla każdego aktywnego obozu
  → wykonuje skonfigurowane reguły automatyzacji
  → zapisuje zdarzenia w bm_camp_workflow_events
```

### 5.5 Deklaracja dzienna teczki (frontend)

```
1. Kadra otwiera zakładkę "Teczka" → sekcja "Deklaracja"
2. GET /panel/folder/declaration (nagłówek deklaracji + ostatni dzień)
3. POST /panel/folder/declaration/day (panelNonce, per-dniowe wpisy)
4. Wpisy: zakwaterowanie (typy + liczby), diety (typy + liczby)
```

## 7. Role, uprawnienia i bezpieczeństwo

### 7.1 Capabilities

| Capability | Przypisane do | Zakres dostępu |
|---|---|---|
| `manage_basemgmt` | Administrator (przy aktywacji) | Pełny dostęp do systemu |
| `manage_bm_camps` | Administrator (przy aktywacji) | Obozy i powiązane funkcje |
| `manage_bm_staff` | Administrator (przy aktywacji) | Zarządzanie kadrą |
| `manage_bm_announcements` | Administrator (przy aktywacji) | Moderacja ogłoszeń |
| `manage_options` | Administrator (wbudowane WP) | Ustawienia i licencja |

### 7.2 Zabezpieczenia frontendu

| Mechanizm | Implementacja |
|---|---|
| **Sesje** | Token SHA-256 w DB, raw token tylko w ciastku. HttpOnly + SameSite=Strict + Secure (HTTPS) |
| **Kody dostępu** | `wp_hash_password()` / `wp_check_password()` (bcrypt) |
| **Rate limiting** | 3 nieudane próby → 15-min blokada → trwała blokada (wymaga odblokowania przez admina) |
| **Nonce REST** | `bm_login` (login), `bm_panel` (mutacje panelu), `wp_rest` (nagłówek X-WP-Nonce) |
| **Anti-enumeration** | Identyczny komunikat błędu niezależnie od powodu niepowodzenia |
| **Timing attack** | `wp_hash_password()` wywoływane przy każdej próbie (równe czasy odpowiedzi) |
| **Path traversal** | `realpath()` + walidacja katalogu `uploads/basemgmt/` przy pobieraniu plików |

### 7.3 Zabezpieczenia admina

| Mechanizm | Implementacja |
|---|---|
| **Nonce formularzy** | `check_admin_referer()` w każdym `handle_*()` |
| **Capability checks** | `current_user_can()` przed każdą operacją |
| **Prepared statements** | `$wpdb->prepare()` we wszystkich zapytaniach |
| **Output escaping** | `esc_html()`, `esc_attr()`, `esc_url()`, `wp_kses_post()` |
| **SRI** | Integrity hash dla Alpine.js, Sortable.js, FullCalendar (CDN) |

### 7.4 Znane ograniczenia i obserwacje bezpieczeństwa

1. **`OperationLogger::get_ip()`** – odczytuje `HTTP_X_FORWARDED_FOR` (spoofable). Wpływ tylko informacyjny (logowanie).
2. **`EmailService::send()`** – używa `remove_all_filters()` na hookach `wp_mail_*` po wysłaniu, co może zakłócić inne wtyczki. Rekomendacja: targeted `remove_filter()`.
3. **CDN Alpine.js** – ładowany na każdej stronie frontendowej (nie tylko panelu). SRI hash ustawiony.
4. **Brak nonce na REST mutacjach komunikacji** – `create_reservation`, `reply`, `create_thread` polegają na sesji + SameSite=Strict (akceptowalne).
5. **`BASEMGMT_MAX_ATTEMPTS = 3`** – stała nieedytowalna z UI (tylko przez `bm_lockout_minutes` w opcjach).
